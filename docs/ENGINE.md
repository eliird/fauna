# Fauna Engine — Technical Guide

## Overview

The engine is a Rust application compiled to WebAssembly (WASM) that renders graphics in the browser using wgpu. The React web app loads the WASM bundle and gives it a canvas to draw on.

```
Rust source code
    → wasm-pack compiles to .wasm + .js glue
        → React loads the .js glue
            → .js glue loads the .wasm binary
                → WASM takes over a <canvas> and renders via GPU
```

## How the Code Works (lib.rs)

### Initialization (`init` function)

Called once from JavaScript when the page loads. It sets up everything the GPU needs:

**1. Instance** — entry point to the graphics system.
```rust
let instance = wgpu::Instance::new(&wgpu::InstanceDescriptor {
    backends: wgpu::Backends::GL,  // Use WebGL2 backend
    ..Default::default()
});
```
We use `Backends::GL` to target WebGL2, which has broad browser support.

**2. Surface** — the bridge between the GPU and the HTML canvas.
```rust
let surface = instance.create_surface(wgpu::SurfaceTarget::Canvas(canvas)).unwrap();
```
The GPU can't draw directly to a canvas. It draws to a surface, and the surface is connected to the canvas.

**3. Adapter** — represents the physical GPU hardware.
```rust
let adapter = instance.request_adapter(&wgpu::RequestAdapterOptions {
    compatible_surface: Some(&surface),
    ..Default::default()
}).await.unwrap();
```
We ask for a GPU that's compatible with our surface. This is async because the browser needs time to query the GPU.

**4. Device and Queue** — your interface to the GPU.
```rust
let (device, queue) = adapter.request_device(
    &wgpu::DeviceDescriptor {
        required_limits: wgpu::Limits::downlevel_webgl2_defaults(),
        ..Default::default()
    },
).await.unwrap();
```
- **Device** — used to create buffers, shaders, pipelines, textures.
- **Queue** — where you submit commands for the GPU to execute.
- **downlevel_webgl2_defaults()** — only request capabilities WebGL2 actually supports (no compute shaders, etc.).

**5. Surface Configuration** — tells the surface what format and size to use.
```rust
surface.configure(&device, &config);
```
Must be called before you can render. Sets the pixel format, dimensions (800x600), and present mode.

**6. Shader** — a program that runs on the GPU.
```rust
let shader = device.create_shader_module(wgpu::ShaderModuleDescriptor {
    source: wgpu::ShaderSource::Wgsl(include_str!("shader.wgsl").into()),
    ..
});
```
`include_str!` embeds the shader file contents into the WASM binary at compile time.

**7. Render Pipeline** — the complete recipe for how to turn data into pixels.
```rust
let pipeline = device.create_render_pipeline(&wgpu::RenderPipelineDescriptor { .. });
```
Specifies:
- Which shader to use (vertex + fragment entry points)
- What vertex data format to expect (`buffers`)
- What kind of shapes to draw (`TriangleList`)
- What output format (`ColorTargetState` matching the surface)
- How to blend colors (`REPLACE` — overwrite, no transparency)

### The State Struct

Holds everything that persists between frames:
```rust
struct State {
    device: wgpu::Device,
    queue: wgpu::Queue,
    surface: wgpu::Surface<'static>,
    pipeline: wgpu::RenderPipeline,
    frame: RefCell<u64>,
}
```
`RefCell<u64>` is used for the frame counter because `render` takes `&self` (immutable reference) but we need to increment the counter each frame. `RefCell` allows interior mutability — runtime borrow checking instead of compile-time.

### Rendering (`render` method)

Called ~60 times per second by the browser's animation frame loop. Each call draws one frame:

**1. Get a texture to draw on:**
```rust
let output = self.surface.get_current_texture().unwrap();
let view = output.texture.create_view(&Default::default());
```
The surface gives you a fresh blank texture each frame. The `view` is a reference to that texture usable in render commands.

**2. Create a command encoder:**
```rust
let mut encoder = self.device.create_command_encoder(&Default::default());
```
You don't talk to the GPU directly. You record a batch of commands into an encoder, then submit them all at once. More efficient than one-at-a-time.

**3. Begin a render pass:**
```rust
let mut render_pass = encoder.begin_render_pass(&wgpu::RenderPassDescriptor {
    color_attachments: &[Some(wgpu::RenderPassColorAttachment {
        view: &view,
        ops: wgpu::Operations {
            load: wgpu::LoadOp::Clear(wgpu::Color { r, g, b, a }),
            store: wgpu::StoreOp::Store,
        },
        ..
    })],
    ..
});
```
A render pass is a batch of draw operations targeting one set of textures. `LoadOp::Clear` fills the texture with a color before drawing. `StoreOp::Store` means keep the result.

**4. Draw:**
```rust
render_pass.set_pipeline(&self.pipeline);
render_pass.draw(0..3, 0..1);
```
`set_pipeline` tells the GPU which recipe to use. `draw(0..3, 0..1)` means "draw 3 vertices (one triangle), 1 instance." The GPU runs the vertex shader 3 times, figures out which pixels are inside the triangle, then runs the fragment shader on each of those pixels.

**5. Submit and present:**
```rust
self.queue.submit(std::iter::once(encoder.finish()));
output.present();
```
`submit` sends the recorded commands to the GPU. `present` swaps the finished texture onto the screen — without it, the GPU draws but you never see the result.

### Render Loop

Browsers don't support blocking loops (`loop {}`— that would freeze the page). Instead we use `requestAnimationFrame`:

```rust
let f: Rc<RefCell<Option<Closure<dyn FnMut()>>>> = Rc::new(RefCell::new(None));
let g = f.clone();

*g.borrow_mut() = Some(Closure::new(move || {
    state_clone.render();
    window.request_animation_frame(f.borrow()...);
}));

window.request_animation_frame(g.borrow()...);
```

**How this works:**
1. `init()` tells the browser "call this closure on the next frame"
2. The closure calls `render()`, then asks the browser "call me again next frame"
3. The browser calls it again → render → request next frame → repeat

The `Rc<RefCell<Option<Closure>>>` is a Rust ownership dance that lets a closure reference itself. You write it once and never touch it again.

- `Rc` — shared ownership (multiple references to the same data)
- `RefCell` — allows mutation through a shared reference (runtime borrow check)
- `Option<Closure>` — we create the closure after the container, then stuff it in

## Shader (shader.wgsl)

Written in WGSL (WebGPU Shading Language). Contains two functions that run on the GPU:

### Vertex Shader (`vs_main`)
Runs once per vertex. Takes a vertex index and returns a screen position.
```wgsl
@vertex
fn vs_main(@builtin(vertex_index) in_vertex_index: u32) -> @builtin(position) vec4<f32> {
    // Returns position based on vertex index
}
```
Coordinates go from -1.0 to 1.0 in both axes, with (0,0) at center. `vec4(x, y, z, w)` — the `w` component is always 1.0 for positions.

### Fragment Shader (`fs_main`)
Runs once per pixel inside the shape. Returns a color.
```wgsl
@fragment
fn fs_main() -> @location(0) vec4<f32> {
    return vec4<f32>(1.0, 0.5, 0.2, 1.0);  // orange
}
```
`@location(0)` means output to the first color attachment (our canvas texture). Color values are 0.0 to 1.0 (RGBA).

## The Vertex Struct

```rust
#[repr(C)]
#[derive(Copy, Clone, bytemuck::Pod, bytemuck::Zeroable)]
struct Vertex {
    position: [f32; 3],  // x, y, z
    color: [f32; 3],     // r, g, b
}
```

- `#[repr(C)]` — lays out memory in C-compatible order so the GPU reads fields correctly
- `Pod` (Plain Old Data) — tells bytemuck this struct is safe to interpret as raw bytes
- `Zeroable` — the struct can be safely zero-initialized

This struct is what we'll use to pass vertex data from Rust to the GPU via vertex buffers.

## React Side (App.jsx)

Minimal React component that:
1. Renders a `<canvas id="canvas" width={800} height={600}>`
2. On mount (`useEffect`), dynamically imports the WASM glue JS, initializes the WASM module, then calls `init()`

```jsx
useEffect(() => {
    async function startEngine() {
        const wasm = await import('./engine/engine.js');
        await wasm.default();   // Load WASM binary
        await wasm.init();      // Call our Rust init function
    }
    startEngine();
}, []);
```

The `[]` dependency array means this runs once on mount, not on every re-render. React owns everything outside the canvas (page layout, UI, navigation). The WASM engine owns everything inside the canvas.

## Key Concepts Glossary

| Term | What it is |
|------|-----------|
| **WASM** | WebAssembly — a binary format that runs in browsers at near-native speed |
| **wgpu** | Rust graphics library abstracting over WebGPU, WebGL2, Vulkan, Metal, DX12 |
| **Surface** | The connection between GPU rendering and the HTML canvas |
| **Adapter** | Represents the physical GPU |
| **Device** | Your logical handle to the GPU — creates resources |
| **Queue** | Where you submit command batches for the GPU |
| **Shader** | Small program that runs on the GPU (vertex + fragment) |
| **Vertex Shader** | Runs per vertex — positions geometry on screen |
| **Fragment Shader** | Runs per pixel — determines color |
| **Pipeline** | Complete recipe: shader + vertex format + output format + blend mode |
| **Render Pass** | A batch of draw operations targeting specific textures |
| **Command Encoder** | Records GPU commands before submitting them as a batch |
| **Uniform Buffer** | GPU memory for values that are the same across all vertices/pixels in a draw call (e.g., camera matrix, time) |
| **Bind Group** | Links a buffer to a shader slot so the shader can read it |
| **WGSL** | WebGPU Shading Language — the shader language used by wgpu |
| **`bytemuck`** | Converts Rust structs to raw bytes for GPU buffers |
| **`glam`** | Math library for vectors (Vec3) and matrices (Mat4) |

## What's Next

The current state draws a hardcoded triangle with a pulsing background. The next steps to build a 3D coordinate system:

1. **Vertex buffers** — pass vertex data (positions + colors) from Rust to the GPU instead of hardcoding in the shader
2. **Camera uniform** — a view-projection matrix sent to the shader each frame so it can project 3D coordinates to 2D screen space
3. **Axis lines** — X (red), Y (green), Z (blue) lines drawn using `LineList` topology
4. **Input handling** — keyboard/mouse events to move and rotate the camera
5. **Primitive meshes** — cube and sphere vertex data for placing objects in the scene
